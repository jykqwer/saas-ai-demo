# RAG 检索优化实践报告

本文既是工程设计记录，也可直接用于面试、技术评审或项目汇报。所有性能数据均来自仓库内
约 10 MiB 的合成产品手册和同一台开发机上的重复测试，不把演示数据包装成生产结论。

## 一、项目背景

云枢 CloudHub 助手需要从价格、部署、安全、API 和 FAQ 等 Markdown 文档中检索事实，
再交给大模型生成答案。初版为了零外部依赖，使用中文二元组和英文单词组成的 BM25。

小知识库只有 6 篇文档、26 个分块时功能可运行，但抽样发现：

| 用户问题 | 优化前表现 |
| --- | --- |
| 标准版多少钱 | 错误召回免费试用，没有命中价格章节 |
| 你们收费贵不贵 | 无结果 |
| 数据会不会泄露 | 无结果 |
| 怎么找回账号密码 | 正确命中 FAQ |
| 退款政策是什么 | 无结果，属于正确拒答 |
| 今天天气怎么样 | 无结果，属于正确拒答 |

扩展到 10 MiB、20,122 个分块后，问题进一步暴露：每次查询都会为全部分块重新分词、统计
词频并建立局部倒排索引，导致单次查询接近 1 秒，峰值内存超过当前 512 MiB Pod 限制。

## 二、根因分析

1. **标题没有进入索引**：例如“标准版”只写在 Markdown 标题中，正文只有“每位每月
   99 元”，所以精确业务问题反而无法命中正确章节。
2. **章节层级丢失**：初版只保留最后一级标题，多个同名小节无法区分所属文档和父章节。
3. **口语与文档术语不一致**：“收费贵不贵”与“按席位计费”、“数据会不会泄露”与
   “存储加密、访问控制”没有直接词面重合。
4. **复合编号不可部分匹配**：带连字符的场景编号被当成一个完整词，用户省略校验后缀后
   无法召回。
5. **查询阶段重复建索引**：加载时虽然已经有倒排结构，查询时却重新扫描全部分块，时间和
   临时内存都随知识库规模线性增长。
6. **只看 BM25 分数会产生假阳性**：天气问题可能仅因为“怎么样”命中 FAQ，固定分数阈值
   无法表达查询词覆盖程度。

## 三、核心改进

### 1. 章节感知分块

解析 Markdown 的 `# / ## / ###` 层级，并把完整路径写入分块元数据：

```text
价格与套餐 > 标准版
数据安全与合规 > 访问控制
```

分块上限由 420 字调整为 700 字，仍优先按段落边界拆分。这样可以减少事实与适用条件被切到
不同分块的概率，也减少大文档的分块碎片。

### 2. 字段加权 BM25

不再只索引正文，而是按字段设置权重：

| 字段 | 权重 | 原因 |
| --- | ---: | --- |
| 正文 | 1.0 | 主要事实内容 |
| 文档名 | 1.5 | 提供产品域和文件主题 |
| 完整章节路径 | 2.5 | 对价格、版本、功能名称等意图判别最强 |

权重不是凭空追求越大越好，而是保证标题能够纠正正文中的高频噪声，同时不覆盖正文事实。

### 3. 低权重查询扩展

为产品领域维护一组可审计的口语归一化规则，例如：

```text
多少钱、收费、贵不贵 → 价格、计费、报价、套餐
自己的集群、本地部署 → 私有化部署、Kubernetes、Docker
数据会不会泄露 → 数据安全、加密、权限、审计、脱敏
找回密码、登录不上 → 忘记密码、重置密码、账号锁定
```

扩展词权重为原查询词的 0.65，原问题始终占主导。相比让 LLM 每次改写查询，这种方案延迟
稳定、无额外费用、容易测试；缺点是需要随业务词汇持续维护。

### 4. 复合标识符归一化

英文、数字、下划线、点和连字符组成的词同时保留完整 token 和各组成部分。因此用户查询
`cloudhub-deploy-000008` 时，可以命中文档中的
`cloudhub-deploy-000008-3c4538a2c775`，同时完整编号仍具有最高区分度。

### 5. 加载时预构建倒排索引

优化前：

```text
每次查询 → 扫描全部分块 → 重新分词 → 重建局部索引 → BM25 排序
```

优化后：

```text
应用启动/文档变更 → 一次性建立字段加权倒排索引
每次查询          → 只遍历命中词的 posting → BM25 排序
```

`KnowledgeChunk` 不再永久保存完整 token 元组，减少一份大规模字符串引用；按文档过滤也复用
预构建的 `source → chunk indexes`，不再扫描全部分块。

### 6. 查询覆盖率拒答

除最低 BM25 分数外，增加原查询词覆盖率和扩展词命中数判断：

- 原查询至少覆盖 25%；或
- 至少命中 2 个领域扩展词。

这让“收费贵不贵”“数据会不会泄露”可以通过语义别名召回，同时让“退款政策是什么”与
“今天天气怎么样”保持无结果，避免模型拿无关片段强行作答。

## 四、量化成效

### 测试口径

- 基线代码：提交 `df8d899` 中的旧检索实现。
- 测试文档：`backend/rag_testdata/cloudhub-product-manual-10mb.md`。
- 文档大小：10,487,759 字节。
- 分块数量：20,122。
- 查询集合：从 1,829 个场景中等距抽取 20 个，只提供去掉校验后缀的部分锚点。
- 每组数据在独立 Python 进程中运行，统计同进程连续查询的 P50/P95 和最大 RSS。

| 指标 | 优化前 | 优化后 | 变化 |
| --- | ---: | ---: | ---: |
| 部分锚点 Top-1 | 1/20（5%） | 20/20（100%） | +95 个百分点 |
| 查询 P50 | 1011.8 ms | 63.4 ms | 降低约 93.7%，约 16 倍 |
| 查询 P95 | 1117.2 ms | 199.4 ms | 降低约 82.1% |
| 最大查询延迟 | 1136.8 ms | 238.7 ms | 降低约 79.0% |
| 峰值 RSS | 602,724 KiB | 348,988 KiB | 降低约 42.1% |
| 加载建索引 | 2.98 s | 3.83 s | 增加约 28.5% |

加载时间增加是有意的计算前移：应用启动或知识库变更时多做一次字段加权索引，换取后续每次
用户查询显著降低延迟和临时内存。对于读多写少的产品知识库，这是更合适的权衡。

需要注意，348,988 KiB 是独立基准进程的峰值，不包含完整 FastAPI、数据库连接和并发请求的
额外开销，不能直接等同于“512 MiB Pod 一定安全”。如果把整份 10 MiB 材料作为线上知识库，
仍应执行容器级压力测试；内存余量不足时，应提高后端限制或改用持久化索引/独立检索服务。

小知识库回归结果：

| 问题 | 优化后 Top-1 |
| --- | --- |
| 标准版多少钱 | `pricing/价格与套餐 > 标准版` |
| 你们收费贵不贵 | `pricing` 价格文档 |
| 能不能部署在自己的集群 | `deployment/私有化部署` |
| 支持单点登录吗 | `faq/支持哪些单点登录` |
| 数据会不会泄露 | `security/数据加密` |
| 怎么找回账号密码 | `faq/忘记密码怎么办` |
| 退款政策是什么 | 无结果 |
| 今天天气怎么样 | 无结果 |

## 五、如何复现

重新生成确定性测试材料：

```bash
./scripts/generate-rag-test-document.py
```

运行大文档基准：

```bash
./scripts/benchmark-rag.py --samples 20
```

运行纯检索回归测试：

```bash
cd backend
../.venv/bin/python -m pytest tests/test_rag_retrieval.py -q
```

## 六、面试或汇报讲述模板

### 60 秒版本

> 项目最初使用零依赖 BM25 做产品知识库检索，小数据能运行，但出现了标题不参与索引、口语
> 问法召回失败，以及大文档每次查询重建索引的问题。我先构造了一份 10 MiB、两万多个分块、
> 带 1829 组标准答案的确定性测试文档，建立准确率、P50/P95 和内存基线。随后实现章节路径
> 感知分块、标题字段加权、低权重领域查询扩展、复合编号拆分、预构建倒排索引和覆盖率拒答。
> 在相同 20 条部分编号查询上，Top-1 从 5% 提升到 100%，P50 从约 1 秒降到 63 毫秒，
> 峰值内存降低约 42%。代价是启动建索引增加约 0.85 秒，这是读多写少场景下可接受的计算
> 前移。整个第一阶段不依赖外部 Embedding，成本和部署复杂度没有增加。

### STAR 展开方式

- **Situation**：小规模 BM25 演示可用，但真实问法和大文档暴露准确率、延迟、内存问题。
- **Task**：在不增加外部服务的条件下，提高召回质量，并让 10 MiB 文档可用于持续评测。
- **Action**：先构建可复现 golden dataset，再从分块、索引字段、查询理解、复杂度和拒答五个
  层面改造；为每项措施补独立回归测试和统一基准脚本。
- **Result**：Top-1 5% → 100%，查询 P50 下降约 93.7%，峰值内存下降约 42.1%，并明确
  记录加载时间上升的工程权衡。

## 七、局限与下一阶段

当前版本仍是词汇级检索。规则没有覆盖的新同义表达、跨语言查询、长问题中的隐含意图，以及
需要综合多个相距较远章节的问题，仍可能召回不足。下一阶段建议采用混合检索：

```text
BM25 Top-20 + Embedding Top-20 → RRF 融合 → Reranker Top-5 → 模型生成并精确引用
```

这一阶段才需要外部资源：

1. **Embedding**：资源受限 k3s 优先使用外部 Embedding API；需要提供 API 地址、密钥、模型名
   和向量维度。若必须本地化，可独立部署中文 Embedding 服务，不建议塞进当前 512 MiB 后端。
2. **向量存储**：可把现有 PostgreSQL 切换为带 pgvector 的镜像并增加迁移；也可独立使用
   Qdrant。需要先确认备份、升级和资源预算。
3. **Reranker**：高准确率场景可增加外部 Rerank API 或独立模型服务，避免占用 API Pod 内存。
4. **离线索引持久化**：当前文档变更会在进程内重建索引；多副本生产环境还需要对象存储、
   索引版本、原子切换和副本一致性。
5. **更完整评测**：当前大文档主要验证精确事实与性能。正式上线前应加入真实客服问题，统计
   Recall@K、MRR、无答案准确率、引用正确率和最终回答忠实度。

第一阶段不需要申请任何外部模型或额外服务；只有进入混合语义检索时才需要上述资源。
